# 早睡系统 — 全平台一致性与风险排查报告

> 补充 V5 方案，针对跨平台一致性和未暴露的问题

---

## 一、跨平台一致性策略

### 1.1 统一原则

> **同一套 UI、同一套文案、同一套交互逻辑。**
> 底层数据来源不同，但用户看到的是同一个 App。

```
用户眼中：                底层（用户看不见）：
┌─────────────────┐      ┌──────────────────┐
│  📱 昨晚 App 排行 │      │  iOS: DeviceActivity│
│                  │      │  系统渲染报告       │
│  抖音 ██████      │  ←  │  Android: UsageStats│
│  微信 ████        │      │  直接读取          │
│  小红书 ██        │      │  鸿蒙: 使用统计     │
└─────────────────┘      └──────────────────┘

UI 组件完全一样，数据灌入方式不同
```

### 1.2 各功能的一致性方案

| 功能 | iOS 数据源 | Android 数据源 | 鸿蒙数据源 | 用户看到的 UI |
|------|-----------|---------------|-----------|-------------|
| **就寝/起床打卡** | 用户主动 + Siri | 用户主动 + App Actions | 用户主动 + 小艺 | **完全一致** |
| **宵禁检测** | DeviceActivityReport（系统渲染） | UsageStats（直接读取） | 使用统计（直接读取） | **同一张卡片布局** |
| **App 使用排行** | DeviceActivityReport（系统渲染饼图） | UsageStats（直接读，自己画图） | 直接读，自己画图 | **一样的排行榜样式** |
| **睡眠时长** | HealthKit | Health Connect | 运动健康 | **完全一致** |
| **App 锁定** | Shield API（原生） | 专注模式引导/通知 | 待定 | **体验一致**（底层不同） |
| **语音打卡** | Siri Shortcuts | App Actions + 小爱/小布 | 小艺 | **完全一致** |
| **成就/奖励** | 本地计算 | 本地计算 | 本地计算 | **完全一致** |
| **AI 建议** | 统计 + Core ML（本地） | 统计 + ML Kit（本地） | 统计（本地） | **完全一致** |

### 1.3 iOS 报告渲染的特殊处理

iOS 的 DeviceActivityReport 是系统自己画图的，App 拿不到原始数据。为了让 UI 一致：

```
做法：
  DeviceActivityReport 生成报告后，App 通过回调获取关键指标：
  · 总使用时长（分钟）
  · 使用最多的 3 个 App 名称和时长
  · 解锁次数
  
  这些指标足以渲染和 Android 一模一样的排行榜 UI。
  不需要自己画饼图——系统画的饼图和 App 自己的排行榜可以并存。
  
  最终效果：
  ┌──────────────────────┐
  │  📱 睡前 App 使用     │
  │                      │
  │  ① 抖音     1h20m   │  ← 自己渲染，各平台一致
  │  ② 微信      45m    │
  │  ③ 小红书     8m    │
  │                      │
  │  [系统详细报告]       │  ← iOS 特有，系统渲染
  └──────────────────────┘
```

## 二、未暴露的风险与问题

### ⚠️ 风险 1：iOS 的 AI 分析拿不到 App 级别数据

```
问题：
  iOS 的 DeviceActivityReport 是系统渲染的。
  App 进程能收到"使用超时了"的事件回调，
  但拿不到"用户昨晚刷了哪些 App、各多久"的原始数据。

影响：
  AI 分析能用这些数据：
  ✅ 睡眠时间趋势（来自 HealthKit）
  ✅ 宵禁达标率（来自打卡记录）
  ✅ 心情与睡眠相关性（来自手动记录）
  ✅ 按星期几的睡眠模式
  
  AI 分析不能用这些数据（iOS 上）：
  ❌ "你周二晚上总是在刷抖音"——没有 App 级原始数据
  ❌ "刷小红书超过 30 分钟的夜晚睡得晚一些"——同上

对策：
  · 不影响核心分析（睡眠趋势、达标率、心情相关性）
  · App 级别的深度分析只在 Android/鸿蒙上做
  · iOS 上 AI 建议更侧重于睡眠规律（"你周二总是睡得晚"）
  · 用户不会察觉到差异，因为 UI 上展示的排行榜始终是一样的
```

### ⚠️ 风险 2：Android 没有原生的 Shield API

```
问题：
  iOS 的 Shield API 是系统级功能，到点自动屏蔽 App，体验一流。
  Android 没有同等力度的 API。

可选方案：
  
  A. 通知提醒 + 系统专注模式（推荐，零权限）
     · 到点推送通知 "该睡了"
     · 引导用户手动开启系统"专注模式" / "数字健康" 的休息时间
     · 优点：不需要额外权限，系统自带，Google 推荐
     · 缺点：多了一步手动操作

  B. AccessibilityService（需要辅助功能权限）
     · 监听屏幕变化，检测到用户在刷娱乐 App 时弹出遮罩
     · 优点：功能强大
     · 缺点：用户必须手动开启辅助功能权限
     · 缺点：Google Play 可能以"非辅助功能目的"为由拒绝上架

  C. 自己 App 内的软屏蔽
     · App 内检测到用户在锁机时段打开娱乐 App → 推送劝说通知
     · 不能强制，但增加心理阻力
  
  推荐：方案 A + C 组合
  第一版先做 A（通知引导），后续评估要不要做 B
```

### ⚠️ 风险 3：鸿蒙 NEXT 不兼容 React Native

```
问题：
  鸿蒙 NEXT（HarmonyOS 5.0+）不再兼容 Android APK，
  React Native 官方也不支持鸿蒙。

这意味着：
  · 鸿蒙版本需要单独的 ArkTS 代码
  · 不是"一套代码跑三平台"
  · 但 UI 设计稿可以复用（视觉风格一致）
  · 底层能力（使用统计、健康数据）鸿蒙都有对应 API

时间线建议：
  第一版：Android
  第二版：iOS
  第三版：鸿蒙（单独重写 UI 层，复用设计稿）
```

### ⚠️ 风险 4：权限申请流程影响转化率

```
每个需要用户手动操作的步骤，都会流失用户：

iOS 权限链：
  ① 安装 App
  ② 打开 → 弹窗授权 HealthKit → 用户点"允许"
  ③ 打开 → 弹窗授权通知 → 用户点"允许"
  ④ 需要去 设置→屏幕使用时间→打开"共享跨设备数据"
  ⑤ 需要去 快捷指令 App 添加 Siri 短语（可选）
  
  流失风险点：④（用户可能找不到）
  对策：第一次打开时做截图式引导页

Android 权限链：
  ① 安装 App
  ② 打开 → 引导页 → 用户去 设置→使用情况访问权限→开启
  ③ 弹窗授权通知 → 用户点"允许"
  ④ 引导添加小爱/小布快捷指令（可选）
  
  流失风险点：②（步骤最多）
  对策：第一步就展示清晰的"为什么需要这个权限"说明
```

### ⚠️ 风险 5：DeviceActivity Extension 必须在真机调试

```
  · DeviceActivity Monitor Extension 和 Report Extension
    不能在 iOS 模拟器上运行
  · 必须连真机调试
  · Shield API 同理
  
  这意味着：
  · iOS 开发必须有 Apple Developer 账号
  · 必须有一台 iPhone 实机
```

### ⚠️ 风险 6：后台监测的局限性

```
iOS BGTaskScheduler：
  · 系统不保证准时唤醒
  · 主要用于"在合适的时间做维护"，不是精确计时
  · App 被杀死后可能不触发
  
Android WorkManager：
  · 更可靠，但受各厂商省电策略影响
  · 小米/OPPO/华为都有各自的"受保护应用"列表
  
影响：
  宵禁到点的提醒可能延迟几分钟，很正常
  起床检测也一样——系统说了算
```

## 三、各平台最终对比

| | iOS | Android | 鸿蒙 |
|--|-----|---------|------|
| **UI 层** | React Native | React Native | ArkTS（单独开发） |
| **宵禁检测** | DeviceActivity Report | UsageStats | 使用统计 API |
| **App 锁定** | Shield API（原生） | 通知+专注模式引导 | 待调研 |
| **睡眠数据** | HealthKit | Health Connect | 运动健康 |
| **入睡检测** | 加速度计+麦克风（可选） | 加速度计 | 加速度计 |
| **语音** | Siri Shortcuts | App Actions+品牌AI | 小艺 |
| **AI 分析** | 统计+Core ML（无 App 级原始数据） | 统计+ML Kit（完整数据） | 统计 |
| **一致性** | UI ✅ / 分析 ⚠️ | UI ✅ / 分析 ✅ | UI ✅（单独开发） |

## 四、结论

**主要问题就一个：iOS 的 AI 分析拿不到 App 级别原始数据。** 
但这不影响用户看到的 UI 和核心体验——排行榜、图表、建议都有，只是深度分析时 iOS 偏重睡眠模式，Android 可以多做 App 行为分析。

其他问题都有明确的应对方案。
